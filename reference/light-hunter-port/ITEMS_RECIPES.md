## 星阵物品

- 星阵、压缩星阵保留上游 PNG 与动画元数据，均为 16×496、31 帧、每帧 3 tick；没有缩放或改画。
  上游单层 `minecraft:item/generated` 模型转为 1.7.10 原生物品图标，模型 JSON 只保存作来源参考。
- 以 `GTNGItem` 注册、赋值中央 `GTNGItemList`。潜行右键主站时，按手中全部物品提交安装；
  普通星阵每件等效 1，压缩星阵每件等效 1024，安装数量由主站的 64 上限截断。
- 按 `ceil(实际安装数 / 单件等效数)` 消耗整件，创造模式不消耗；达到上限时不消耗。
  拆除返还由主站实现，按实际安装数返还普通星阵，不还原压缩态。
- 仅服务器修改安装数量和手中物品；客户端只确认交互，不自行安装。

压缩星阵当前没有生存获取配方。上游 `Misc.kt:136–143` 只是奥术星图压缩模式的运行原料：
144 个黑洞种子、各 64 个永恒/时空纳米蜂群、64 个循环命令方块和 576000 mB Miracle，耗时 600 tick。
真正产出由 `AstralArrayCompressionTrait` 从机器前方区域收集普通星阵，每 1024 枚一批；
基础成功率 30%，在奥术星图嵌入 42441 枚星阵后达到 100%。猎光号本身没有该压缩机制。
本次未移植奥术星图，因此保留压缩物品的图标、1024 等效安装和回收兼容，不发明替代压缩流程。

## 加工兼容与批次规则

- 未满 64 星阵且未安装线程修正仓时，总配额为 `Int.MAX_VALUE × 128 = 274877906816`，对匹配配方公平分配，
  小需求满足后重新分配剩余额度；剩余额度不足每个活跃配方一份时保留，不强行偏给先后某一方。
- 满 64 星阵后每种配方可申请 `Long.MAX_VALUE` 上限，但仍受真实输入、输出容量、总能耗和可表示耗时限制。
- 上游将各配方输出与原 `EU/t × tick × 并行` 汇总成一个批次，没有各配方独立进度条。
  原常规公式为 `d = totalEU / supplyPower`；各能源仓的 `电压×工作安数` 汇总为供电功率，
  若 `d` 超过设定最短时长则按该总功率运行，
  否则使用 `floor(totalEU / minimumDuration)`；时长按 `round(max(d, minimumDuration))`。
  默认最短时长为 20 tick。这保留原整数取整语义，并非承诺每批整数结算严格无舍入差。
- 主站最多 1 个非激光能源仓；工厂最多 2 个非激光能源仓及 1 个激光仓。
  GTNH 的普通能源与多安能源使用不同继承分支，统一按实际仓类型计数。
  多安及无线多安参与工作功率汇总；不以允许的突发输入电流代替额定工作电流。
- 功率语义同时核对 GTLAdditions 固定提交随附的 `libs/gtlcore-1.2.3.2-fix4.jar`，
  Git blob `399807a82dc467658ac7bcb39ad32184a4b4448e`，
  SHA-256 `c44b8212b8d3a210eabd36e3efaf7804e78e25fc44d45f7b0fb048453aaaf346`。
  `javap -c -p` 确认 `EnergyContainerListMixin.EnergyContainerList` 对各仓 V/A 作饱和乘加，
  将总功率写入 `inputVoltage` 并归一为 1A；`WorkableElectricMultiblockMachineMixin.getOverclockVoltage`
  返回聚合输入/输出电压的最大值。两类均列入该 JAR 的 `gtlcore.mixin.json`。
  这两处行为与结构素材所用 GTLCore `6443c848264fb15c90cf50e031f146522616a8b9` 源码一致；
  配方查询和批次释放均使用总功率，没有额外增加原版不存在的单仓电压门槛。
- `LightHunterRecipeRules` 用 BigInteger 避免汇总能量过大时浮点失真，拒绝超 `int` 耗时；
  公平分配使用索引数组，避免原 64 项位图的移位边界问题。
- GTNH 没有独立蒸发配方组，映射为原生无单元化学脱水配方，重复组只保留一份。
- GTNH 基础岩石粉碎机有世界水/岩浆邻接条件；工业版的真实配方为电路 1 圆石、
  电路 2 石头（各 16 tick、30 EU/t），电路 3 加消耗 1 红石粉产黑曜石（128 tick、30 EU/t）。
  本次专用 `LightHunterRockBreakingRecipes` 保留这些结果、时间、能耗与红石消耗，并按主站模块
  无外置水/岩浆结构的适配，每次各消耗 1000 mB 水和岩浆。没有将 fake 展示方直接转为无料产物。

## 可选线程修正仓

保留原 `ThreadPartMachine` 单槽行为：仅放普通星阵，最多 64 颗；星阵不消耗，不接受压缩星阵。
仓内物品与嵌入主站的星阵分别计数；仓内星阵不会解锁主站的 64 星阵模式。
每台卫星工厂最多安装一个，不能作为多个控制器共享的仓，也不是本模组参数仓或执行核心。

上游 `ThreadMultiplierStrategy` 对四类卫星工厂采用默认机器倍率 2，完整公式为：
`round(min(1 / GTLCore.durationMultiplier, 4096) × 2)`；GTLCore 原默认 `durationMultiplier=1`。
GTNH 不具有该全局设置，本移植固定采用原默认结果 2，因此每颗普通星阵提供 `64×2=128` 额外线程。
64 颗提供 8192 额外线程，加上 128 基础线程为 8320；主站未满阵时并行配额为
`Int.MAX_VALUE×8320=17867063943040`。主站满 64 星阵后仍走原每配方无配额上限分支。
线程修正仓改变可合批的配额，不使原配方免能耗。
